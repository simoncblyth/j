Your code is organized in a non-standard way with your 
WaterPoolConstructionEMF.hh not being a proper easy to 
include and use header. Rather your .hh is just 
a piece of code that must be included into a specific place 
in some other code. That is the ultimate in being non-flexible
and is a non-scalable way to organize your C++.

This needs to be corrected in order that others can 
rapidly work out what you are doing.

The standard way to add functionality to WaterPoolConstruction is to 
implement headers and implementation file, eg::

```
    WaterPoolConstructionEMF.hh
    WaterPoolConstructionEMF.cc
```

The header defines the interface methods by which 
the functionality is provided to WaterPoolConstruction
and the API shows how the two are related.

to create a struct/class. eg:

To use this from WaterPoolConstruction.cc you will need to::

Then you can use the methods you define::


It is not inevitable that you will need a "WaterPoolConstructionEMF" object.
I typically start with static methods for small parts of the functionality like 
the above "BuildLProfileSectorPolycone". This is using the struct 
just as a "namespace" to keep your functionality and data.  Subsequently 
I implement the object if it looks more convenient than just using
static methods which are called like the below with no object::

```
    G4Polycone* poly = WaterPoolConstructionEMF::BuildLProfileSectorPolycone(...)
```  
A good convention to follow is to name static methods starting with a uppercase letters
and object methods with lowercase ones.


    
The advantages with this approach are:

1. standard way to use C++ so its easy for others to understand
2. dependencies are made obvious via what you have to pass across the API
3. you header can be included into a test executable to make a standalone test

That code can more clearly and safely be implemented with methods. 

Lambda expressions are able to capture the context from before them.
While they are useful in some situations, this is not such a situation.
Code is written once and read many times, being quick
to read is very important. The lambdas here obscure what you are doing
and introduce dangers that can be avoided using methods.
